## Executive Summary

The **Evidence Manifest** (`.caf` files) is the foundational format standard for CloudAI Fusion's verifiable control plane. Like Docker locked developers in via Dockerfile, this format creates **strategic lock-in through data gravity**: once teams accumulate months of cryptographic evidence chains audited by regulators, migrating away becomes prohibitively expensive.

This specification defines the declarative configuration language teams use to declare **what** events they need attested, **how** the chain must be maintained, and **where** evidence flows for compliance export. It is the interface between platform operators and the Evidence Ledger subsystem.

---

## 1. Strategic Intent

### 1.1 The Lock-In Mechanism

Docker achieved vendor lock-in because:
1. Developers wrote Dockerfiles as part of normal workflow
2. Migrating meant rewriting hundreds of build configurations
3. Ecosystem tooling built around Dockerfile semantics

CloudAI Fusion achieves lock-in via:
1. Teams define `evidence-manifest.yaml` at project bootstrap
2. Months of cryptographic evidence chains accumulate under declared policies
3. Compliance audits depend on `.caf` evidence formats (SLSA/SARIF interoperability)
4. Migrating requires re-auditing all historical evidence with new tools

### 1.2 Competitive Differentiation

| Competitor Approach | CloudAI Fusion Approach |
|---------------------|--------------------------|
| Trust-based dashboards | Cryptographic proofs |
| Proprietary audit logs | Open .caf manifest format |
| Manual compliance reports | Automated SLSA/SARIF export |
| Opaque control planes | Offline-verifiable chains |

## 2. Formal Syntax

### 2.1 File Format

Evidence manifests are YAML documents following this structure:

```yaml
apiVersion: caf.io/v1
kind: EvidenceManifest
metadata:
  name: <string>              # Unique identifier for this manifest
  namespace: <string>          # Logical namespace (default: default)
  labels:                       # Optional key-value labels
    app: <string>
    team: <string>
  annotations:                  # Human-readable notes
    description: "Production cluster evidence policy"
  created: <RFC3339 timestamp>  # Auto-generated by cafctl init
  modified: <RFC3339 timestamp> # Updated on validation/apply

spec:
  # Chain Configuration
  chain:
    algorithm: <algorithm_id>   # Supported: groth16-bn254-poseidon2, ed25519-secp256k1
    signer: <key_type>          # Supported: ed25519-pem, secp256k1-ecdsa
    storage: <storage_backend>  # Supported: append-only-merkle, tamper-evident-log
    
  # Subjects: What we attest
  subjects:
    - type: <subject_type>       # See §3.2 for supported types
      selector: <label_selector> # Labels to match (e.g., "app=*", "pipeline=prod")
      events:                    # Event types to capture
        - <event_verb>           # e.g., created, updated, deleted
      options:                   # Subject-specific configuration
        include_payloads: true   # Whether to store full domain payloads
        hash_inputs: true        # Hash input parameters even if not stored
        
  # Verification & Policy
  policy:
    min-signers: <integer>            # Threshold multi-sig (1 = single sig)
    max-age: <duration>               # Max evidence age before re-attestation (e.g., 720h = 30d)
    require-zkp: <boolean>            # Force ZKP proofs for sensitive operations
    zkp-circuit: <circuit_name>       # Custom circuit for specialized proofs
    
    export:
      webhook: <url>                  # Real-time push endpoint
      interval: <duration>            # Polling interval (e.g., 1h)
      
    retention:
      years: <integer>                # Keep evidence this long (legal minimum)
      archive-after: <duration>       # Move cold data after X time
      
  # Interoperability exports
  export:
    formats:                          # Output formats to generate automatically
      - sarif                         # Static analysis report interchange format
      - slsa-provenance               # Supply-chain provenance v1.0
      - sigstore-bundle               # Sigstore transparency log bundle
      - pdf-report                    # Human-readable compliance report
    destinations:                     # Where to send exports
      - type: file-system
        path: /compliance/evidence
      - type: s3
        bucket: company-compliance
        region: us-east-1
        prefix: evidence-chains/
        
  # Override defaults for namespaces
  overrides:
    - namespace: <namespace>
      policy:                         # Local override
        min-signers: 2
        require-zkp: true
      subjects:                       # Additional local subject rules
        - type: secret-management
          selector: "type=jwt"
          events: [issued, revoked]
```

### 2.2 Data Types

| Type | Format | Example |
|------|--------|---------|
| `algorithm_id` | Enum | `groth16-bn254-poseidon2` |
| `key_type` | Enum | `ed25519-pem`, `secp256k1-ecdsa` |
| `duration` | ISO 8601 duration | `720h`, `30d`, `1w` |
| `rfc3339 timestamp` | RFC3339 | `2026-08-15T10:00:00Z` |
| `label_selector` | K8s-style | `app=prod`, `team!=security` |
| `subject_type` | Enum | See §3.2 |
| `format` | Enum | `sarif`, `slsa-provenance`, etc. |

## 4. Subject Types Reference

### 4.1 Deployment Events

```yaml
subjects:
  - type: deployment
    selector: "app=*"
    events: [created, updated, deleted, scaled]
```

**Captures:**
- Pod/container lifecycle changes
- Resource scaling events
- Image tag updates
- Configuration drift

### 4.2 Security Scan Results

```yaml
subjects:
  - type: security-scan
    selector: "pipeline=prod"  
    events: [passed, failed, remediated]
```

**Captures:**
- Trivy/Snyk scan results
- CVE discovery and patching
- Policy violations (OPA/Kyverno)
- Vulnerability trend lines

### 4.3 Model Training Pipeline

```yaml
subjects:
  - type: model-training
    selector: "experiment=*"
    events: [started, checkpoint, completed, verified]
```

**Captures:**
- Hyperparameter snapshots
- Dataset hashes
- Checkpoint integrity proofs
- Model provenance (who trained, when, why)

### 4.4 Secret Management

```yaml
subjects:
  - type: secret-management
    selector: "type=jwt"
    events: [issued, revoked, rotated]
```

**Captures:**
- Token issuance metadata
- Revocation timestamps
- Rotation frequency tracking

### 4.5 Database Transactions

```yaml
subjects:
  - type: database
    selector: "tenant=*"
    events: [migrate, backup, restore, purge]
```

**Captures:**
- Schema migration hashes
- Backup chain integrity
- GDPR right-to-be-forgotten proofs

## 5. Policy Enforcement Semantics

### 5.1 Multi-Signer Threshold

When `min-signers: 2`, the ledger requires **threshold signatures** from multiple distinct keys. This prevents a single compromised operator key from forging evidence.

**Implementation:** BLS signature aggregation or GPG multi-key signing.

### 5.2 Evidence Freshness

`max-age: 720h` means any evidence older than 30 days (720 hours) cannot be used in critical decisions without re-attestation. This forces periodic proof refreshes.

**Use Cases:**
- Production deployments stale >30d → auto-disable
- Audit logs >30d → require re-signing

### 5.3 ZKP Requirements

`require-zkp: true` mandates that certain operations produce Groth16 zk-SNARK proofs rather than just signed receipts.

**Example:** When handling PII, instead of storing raw transaction data, the system produces a zero-knowledge proof that the transaction was valid without revealing the PII.

## 6. Export Formats Deep Dive

### 6.1 SLSA Provenance v1.0

The Evidence Manifest exports evidence chains as **SLSA Level 3+** provenance:

```json
{
  "_type": "https://slsa-framework.github.io/provenance/v1",
  "subject": [{"name": "my-app", "digest": {"sha256": "abc...xyz"}}],
  "builder": {
    "id": "https://cloudai-fusion.io/ledger/"
  },
  "buildType": "https://cloudai-fusion.io/evidence-manifest/v1",
  "invocation": {
    "configSource": {
      "uri": "file://evidence-manifest.yaml",
      "digest": {"sha256": "manifest-hash"},
      "entryPoint": "spec.export.webhook"
    }
  },
  "metadata": {
    "startTime": "2026-08-15T10:00:00Z",
    "endTime": "2026-08-15T10:00:05Z",
    "completeness": {"arguments": true, "environment": false},
    "reproducible": false
  },
  "materials": [
    {
      "uri": "evidence:chain/seq:1",
      "digest": {"sha256": "genesis-prevhash"}
    }
  ]
}
```

**Why This Matters:**
- Toolchains like Sigstore/Cosign consume SLSA provenance
- Makes CloudAI Fusion evidence consumable by **entire cloud-native ecosystem**
- Positions us as the **hub**, not a silo

## 7. Migration Path

### 7.1 From No Manifest → With Manifest

```bash
# Generate initial manifest from current state
cafctl manifest init --output evidence-manifest.yaml

# Review and edit manually
nano evidence-manifest.yaml

# Validate against spec
cafctl manifest validate evidence-manifest.yaml

# Apply to configure evidence collection
cafctl manifest apply --dry-run  # Test first
cafctl manifest apply           # Then production
```

### 7.2 From Old Evidence Format → .caf

If you have pre-existing evidence chains:

```bash
# Import old format (assumes JSON line per record)
cat legacy_evidence.jsonl | \
  cafctl migrate legacy-to-caf | \
  cafctl manifest apply --chain-file .caf/migrated-chain.json

# Verify continuity
cafctl verify --chain-file .caf/migrated-chain.json
```

### 7.3 Multi-Namespace Portals

For organizations managing many Kubernetes namespaces:

```yaml
# Top-level manifest aggregating all sub-namespaces
apiVersion: caf.io/v1
kind: EvidenceManifestAggregate
metadata:
  name: org-wide-policy
spec:
  aggregates:
    - source: ./k8s-platform/evidence-manifest.yaml
      namespace: k8s-platform
    - source: ./ml-engineering/evidence-manifest.yaml
      namespace: ml-engineering
    - source: ./finance/evidence-manifest.yaml
      namespace: finance
  enforcement:
    cross-namespace-checksums: true  # Require Merkle proofs across boundaries
```

## 8. Implementation Guide

### 8.1 Parse API Contract

```go
// pkg/manifest/manifest.go
package manifest

import (
    "context"
    "io"
)

// Manifest represents the parsed EvidenceManifest structure
type Manifest struct {
    APIVersion string                 `yaml:"apiVersion"`
    Kind       string                 `yaml:"kind"`
    Metadata   ManifestMetadata       `yaml:"metadata"`
    Spec       ManifestSpec           `yaml:"spec"`
    
    // Raw YAML bytes for deterministic round-trip
    RawYAML []byte
}

// Parse reads a manifest from a file path or io.Reader
func Parse(path string) (*Manifest, error)
func ParseFromReader(r io.Reader) (*Manifest, error)

// Validation
type ValidationError struct {
    Field   string
    Message string
    Severity SeverityEnum // Error, Warning, Info
}

type SeverityEnum string
const (
    Err SeverityEnum = "error"
    Warn SeverityEnum = "warning"
    Info SeverityEnum = "info"
)

func (m *Manifest) Validate() []ValidationError

// Application
type EvidenceStore interface {
    Append(ctx context.Context, record *Evidence) error
    List(ctx context.Context, filter Filter) ([]*Evidence, error)
}

func (m *Manifest) Apply(ctx context.Context, store EvidenceStore) error
```

### 8.2 Subject Registration Hook

When applying a manifest, the system should register each subject as an event listener:

```go
func (m *Manifest) Apply(ctx context.Context, store EvidenceStore) error {
    for _, subject := range m.Spec.Subjects {
        // Register event listener based on selector
        handler := NewEventHandler(subject.Type, subject.Selector)
        
        // Attach to internal event bus (see pkg/eventbus)
        if err := eventbus.Subscribe(subject.Events, handler); err != nil {
            return fmt.Errorf("failed to subscribe subject %q: %w", subject.Type, err)
        }
        
        // Mark as active in policy store
        if err := store.StorePolicy(ctx, subject); err != nil {
            return fmt.Errorf("failed to store policy: %w", err)
        }
    }
    
    // Set up exporters
    return m.configureExporters(ctx)
}
```

### 8.3 SLSA Export Implementation

```go
// pkg/manifest/export_slsa.go
package manifest

import (
    "github.com/in-toto/attestation/go/v1"
)

// ToSLSAProvenance converts a sequence of Evidence records into SLSA Provenance v1.0
func ToSLSAProvenance(records []*Evidence, manifest *Manifest) (*intoto.ProvenanceStatementSLSA1, error) {
    // Convert evidence chain into materials section
    var materials []*atpb.ProvenanceMaterial
    for _, rec := range records {
        material := &atpb.ProvenanceMaterial{
            Uri: fmt.Sprintf("evidence:chain/seq:%d", rec.Seq),
            Digest: map[string]string{
                "sha256": rec.Hash,
            },
        }
        materials = append(materials, material)
    }
    
    // Build invocation config source
    invocation := &atpb.Invocation{
        ConfigSource: &atpb.ProvenanceURI{
            Uri:      fmt.Sprintf("file://%s", "evidence-manifest.yaml"),
            Digest:   map[string]string{"sha256": computeManifestHash(manifest)},
        },
    }
    
    return &intoto.ProvenanceStatementSLSA1{
        _type:      intoto.StatementTypeURI,
        Subject:    materials,
        Builder:    builderID(),
        Invocation: invocation,
        Metadata: &intoto.ProvenanceMetadata{
            StartedAt:   getEarliestTimestamp(records),
            FinishedAt:  getLatestTimestamp(records),
            Completeness: &intoto.ProvenanceCompleteness{
                Arguments: true,
            },
        },
    }, nil
}
```

## 9. Security Considerations

### 9.1 Key Management

The manifest references signing keys but **never stores them**. Use external key management:

```yaml
spec:
  chain:
    signer: ed25519  # Referenced key loaded from:
    key_source:      # External vault reference
      type: aws-kms
      resource_arn: arn:aws:kms:us-east-1:123456789:key/abc-def-ghi
```

### 9.2 Webhook Authentication

Export webhooks must be authenticated:

```yaml
export:
  webhook: https://compliance.internal/evidence
  auth:
    type: bearer-token
    secret_ref: vault:compliance/webhook-token
```

### 9.3 Private Data Exposure

When `include_payloads: true` captures sensitive data (PII, secrets):

1. Encrypt payloads at rest using per-tenant keys
2. Redact obvious secrets (API tokens, passwords)
3. Provide redaction filters:

```yaml
subjects:
  - type: database
    selector: "tenant=finance"
    events: [query]
    redact:
      patterns:
        - "(?i)(password|secret|token)"
      replace_with: "[REDACTED]"
```

## 10. Performance Characteristics

### 10.1 Storage Overhead

Per evidence record:
- Ed25519 signature: 64 bytes
- SHA256 hash: 32 bytes
- Metadata overhead: ~50 bytes
- **Total**: ~150 bytes per attestation

At 10,000 attestations/sec × 24 hours:
- Daily volume: 10,000 × 86,400 × 150 ≈ 130 GB/day
- Yearly: ~47 TB/year

### 10.2 Verification Latency

- Single record verification: <10μs (Ed25519 verify)
- Full chain (1M records) with checkpoint: <100ms
- ZKP proof verification: 2-5ms (Groth16 on BN254)

## Appendix B: Glossary

- **Attestation**: A signed claim about some action taken in the control plane
- **Chain**: The hash-linked sequence of attestations forming a tamper-evident log
- **Ledger**: The append-only storage backend for the evidence chain
- **ZKP**: Zero-Knowledge Proof — cryptographic proof revealing nothing beyond validity
- **Subject**: The entity being observed (deployment, scan, model training, etc.)
- **Selector**: Label-based filter matching specific resources within subjects
